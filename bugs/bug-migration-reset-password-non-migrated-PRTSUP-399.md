# Password reset for non-migrated users (PRTSUP-399)

**Primary Jira ticket:** PRTSUP-399

## Summary

A user who has **not yet been migrated** can request a password reset directly from the new mobile app. The new app does not send an OTP/Cognito reset for these users; instead, Core detects the legacy account in the old MySQL database and calls the old Kippy/Petlink API to issue a temporary password.

The temporary password generated by the old API is used directly to create the Cognito account during migration. The user receives it by email or SMS, logs in to the new app with it, and the standard migration flow completes successfully. The migration team has confirmed that the legacy API now generates passwords that comply with the new environment's password policy; that specific behavior is not verifiable from the new-app codebase because the legacy API is not part of this repository.

**Conclusion:** the user does **not** need to open the old app to reset the password, and the reset-before-migration flow is expected to work end-to-end. PRTSUP-399 can be closed unless a specific failure log contradicts this.

## Suggested Jira response (for the end user)

> Yes, the user can reset the password even if they have not yet been migrated, directly from the new app. Here is what they need to do:
>
> 1. From the new app login screen, tap **"Forgot password"**.
> 2. Enter the email or phone number associated with the old account.
> 3. If the account has not been migrated yet, the app detects the user in the legacy database and asks the legacy API to reset the password. Depending on the contact type, the user will receive a message from the legacy system with either instructions or a temporary password (the app copy says: for email, instructions on how to reset the password; for SMS, a temporary password).
> 4. Go back to the new app login screen and enter the same email/phone number again, using the password received or set through the legacy reset process.
> 5. The app will start the migration. Once it completes, the account will be active in the new app.
>
> **Note:** the migration team has confirmed that the temporary/reset password generated by the legacy system is made to comply with the new environment's password requirements, so the migration should complete without password-policy errors.

## Detailed flow

### 1. User taps "Forgot password" in the new app

- Mobile: `AuthViewModel.checkPhoneValidationAndSendOtp()` (`auth_view_model.dart:613`).
- It calls Core GraphQL mutation `sendOtpForgotPassword(contact, appBrand)`.

### 2. Core detects a legacy account

`petlink-everywhere-core/src/lambda_functions/graphql/mutation/sendOtpForgotPassword/handler.ts`:

1. Looks for the user in MongoDB `petlinkEverywhere` by email or phone.
2. If not found, queries the legacy MySQL `user` table with `migrated = 0` and matching contact (lines 178-244).
3. If a legacy user is found:
   - **Phone**: `POST {PETLINK_API_BASE_URL|KIPPY_API_BASE_URL}/request_forgot_password_sms.php` with `country_code` and `phone_number`.
   - **Email**: `POST {PETLINK_API_BASE_URL|KIPPY_API_BASE_URL}/request_forgot_password_token.php` with `registration_email`.
4. If the legacy API returns `return == 0`, Core responds to the app with `translationCode: 'errors.user_should_migrate'` (lines 281-286, 321-326).
5. If the legacy API returns any other value, the handler currently falls through to a generic `404` / `errors.insert_valid_contact` response. This is an implementation detail that may need verification depending on what the legacy API actually returns.

### 3. App tells the user to wait for the temporary password

`petlink-everywhere-mobile/lib/features/auth/presentation/view_model/auth_view_model.dart:676-693`:

- On `errors.user_should_migrate` the app shows `PetLinkWarningDialog`.
- The message uses translations:
  - `register.reset_password_email` → *“An email has been sent to the email address you provided with instructions on how to reset the password.”*
  - `register.reset_password_phone` → *“We have sent you a text message containing a temporary password.”* (`en-US.json:160-162`)
- The user is redirected back to the login/auth screen (`Get.offAndToNamed(Routes.auth)`).

**Important:** the app does **not** continue into the OTP/new-password screen for legacy users, because the new app has no OTP record for them — the old system is the one that generated the reset.

### 4. User logs in with the temporary/new password

1. User enters contact + the temporary password in the login screen.
2. `AuthViewModel.fieldValidation()` (`auth_view_model.dart:440`) calls Core query `checkMigration(contact, password, appBrand)`.
3. `petlink-everywhere-core/src/lambda_functions/graphql/query/checkMigration/handler.ts`:
   - Searches MongoDB.
   - If not found, searches legacy MySQL with `migrated = 0`.
   - Verifies the provided password against the MySQL `password_hash` (SHA-256 with salt).
   - On match, returns `translationCode: 'success.user_can_be_migrated'`.
4. The app shows the migration dialog; on confirm, it calls `startMigration` with the same password.

### 5. Migration creates the Cognito account

- `petlink-everywhere-core/src/lambda_functions/graphql/mutation/startMigration/handler.ts` invokes the `migrationOnDemand` Lambda forwarding `contact`, `password`, `appBrand`.
- `petlink-data-migration/src/lambda_functions/migrationOnDemand/handler.ts`:
  - Builds `effectivePassword = password` for `ON_DEMAND` source (lines 114-115).
  - Creates the user document in MongoDB.
  - Calls `createCognitoUser(...)` with `TemporaryPassword: effectivePassword` and then `AdminSetUserPassword(..., Password: effectivePassword, Permanent: true)` (lines 398-410).
  - If the password is compliant with the Cognito password policy, `adminCreateUser` succeeds. The migration team has confirmed that the legacy reset API now enforces this; this is not verifiable from the new-app codebase.
- Once Cognito is created, the app calls `cognitoManager.signIn()` with the same credentials.

## Conclusion and remaining caveats

Based on the code analysis and the migration team's confirmation:

- The new app can reset the password of a non-migrated user without the user opening the old app.
- Core delegates the reset to the old API, which returns a temporary password.
- The temporary password is generated to meet the new Cognito password policy, so `createCognitoUser` in `migrationOnDemand` accepts it and the migration succeeds.
- The user logs in with the temporary/reset password, `checkMigration` validates it against the legacy hash, `startMigration` creates the Cognito/MongoDB user, and the migration completes.

### What is verified by the code in this repository

- `sendOtpForgotPassword` falls back to the legacy reset API when the user is not in MongoDB and `migrated = 0` in MySQL (`handler.ts:166-327`).
- The app shows a reset dialog and returns to the login screen on `errors.user_should_migrate` (`auth_view_model.dart:676-693`).
- `checkMigration` verifies the provided password against the legacy MySQL `password_hash` (`handler.ts:155-167`).
- `startMigration` and `migrationOnDemand` create the Cognito user with the same password supplied by the user (`startMigration/handler.ts`, `migrationOnDemand/handler.ts:114-115, 398-410`).
- The translation strings `reset_password_email` and `reset_password_phone` describe what the user is told to expect (`en-US.json:160-162`).

### What is not verifiable from this repository

- The exact content and contract of the legacy reset response (email link vs. temporary password string, the meaning of `res.return`, etc.) depends on `request_forgot_password_token.php` and `request_forgot_password_sms.php`, which are not in this repo.
- Whether the legacy API now enforces the new Cognito password policy for temporary/reset passwords is confirmed by the migration team but cannot be checked in the code here.

### What could still go wrong

1. **Handling of `res.return` in `sendOtpForgotPassword`.** If the legacy API returns a non-zero value on success, the current Core code falls through to `errors.insert_valid_contact`. This should be verified against the actual legacy API contract. If the contract is `return == 0` for "must migrate" and non-zero otherwise, the current behavior is intentional.
2. **User confusion about next step.** The app shows a generic "reset password" dialog and sends the user back to the login screen. It should be clear that they must use the temporary password on the login screen, not in an OTP field.
3. **Legacy API not actually generating a compliant password.** The flow depends on the legacy API honoring the new password policy. If it does not, the user would hit `InvalidPasswordException` during migration (the same scenario as PRTSUP-683, but for a different root cause). This would be a deployment/configuration issue on the old system, not a bug in the new flow.

## Notes for closing the ticket

- PRTSUP-399 can be closed as "works as designed" if the observed behavior matches the flow above.
- If a specific user still cannot reset before migrating, the investigation should focus on:
  - the legacy API response for that contact,
  - whether the temporary password reaches the user,
  - whether the temporary password satisfies the Cognito policy,
  - whether the user is entering the temporary password on the login screen (not as an OTP).
